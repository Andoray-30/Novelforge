# NovelForge 模型网关、提取价值与下一步收敛复盘

日期：2026-06-02

## 结论

当前问题不能再被理解为“换一个 API 地址 / 换一个模型名就能解决”。网关下的模型存在速度、结构化能力、中文叙事理解、长上下文稳定性、JSON 合规性和上游 channel 状态差异。慢模型不等于不可用，快模型也不等于适合提取。

NovelForge 的方向必须从“配置一个模型”升级为“按任务角色编排模型”。如果系统把长篇提取完全押在单个模型上，或者在模型失败后只从原文摘录 fallback 资产，那么 AI 的产品价值会被稀释为“搬运文本”，项目也会在每次网关波动时重新不可用。

AI 在 NovelForge 中的价值不是替代章节解析、切分、证据定位这些确定性工程能力，而是完成规则系统无法稳定完成的语义判断：角色性格、人物动机、关系张力、事件意义、世界观规则、写作时的情绪推进和叙事选择。

## 2026-06-02 补充判断

本轮需要暂停继续堆功能。当前真正的风险是：系统表面接入了 AI，但如果首轮提取失败后只是靠规则摘录原文片段，或者每次网关变化都手工替换一个模型名，那么产品仍然没有形成稳定的 AI 创作能力。

必须把问题拆成三层处理：

- **规则层**：保证编码、切章、分段、证据定位、失败章节记录和候选召回稳定。
- **模型编排层**：按任务角色选择模型，区分快模型、慢模型、结构化模型、写作模型和 judge 模型。
- **质量闭环层**：判断资产是否真正可用于写作，并把低置信、fallback、需 repair 的资产暴露给用户和 agent。

只有三层同时成立，AI 才不是“把文章搬进数据库”，而是把小说正文转成可写作的项目记忆库。

## 当前遇到的问题

### 1. 网关可达不代表模型可用

浏览器能打开网关、`/models` 能返回列表、短 prompt 能回复，都只能说明基础连接存在。它不能证明模型适合长篇小说提取。

长篇提取至少要求模型同时满足：

- 长章节输入不超时、不空响应。
- 能稳定输出可解析 JSON。
- 能返回角色、关系、事件、世界观候选，而不是空数组或泛泛摘要。
- 能提供 evidence，且 evidence 与资产字段一致。
- 不把关系端点写成抽象概念、残缺别名或错别字。
- 不让时间线 title 和 description 错配。
- 能把关系从“认识 / 朋友”推进到依赖、误解、债务、冲突、情绪张力和场景潜力。

因此，连接检查只能是第一层 probe，不应作为提取可用性的验收。

### 2. 模型速度不是唯一指标

当前网关模型大致会出现几类情况：

- 快但浅：响应快，适合候选召回、灵感、短段落，但可能返回浅摘要或低质量关系。
- 慢但深：适合复杂关系、世界观规则、正式序章和关键章节，但不适合高并发扫全书。
- JSON 稳定但写作弱：适合结构化提取和修复，不适合文学表达。
- 写作强但结构化弱：适合序章 / 改写，不适合强 JSON schema。
- 阶段性波动：同一模型在不同时段可能受上游 channel 影响，出现空响应、504、429 或长延迟。

所以策略不是寻找一个万能模型，而是给不同任务分配不同模型角色。

慢模型需要被更精确地分类，不能简单判为不可用：

- **慢但成功**：可以进入 `extractor_deep`、`writer_pro`、`judge`，只处理高价值资产和正式写作。
- **慢且空响应**：需要降低输入长度、切换角色池或进入 cooldown。
- **慢且 JSON 不稳定**：不适合 extractor 主链路，但可能适合 writer。
- **快但质量浅**：适合候选召回和灵感，不应直接决定 `completed`。
- **快且结构化稳定**：适合 `extractor_fast` 主扫和 repair 的第一候选。

因此，实时测速不能只得到“快 / 慢”结论，还要得到“适合什么任务”的结论。

### 3. 当前路由已经起步，但还不是完整编排

已落地能力：

- `extractor_fast / extractor_deep / extractor_repair / writer_fast / writer_pro / judge` 角色池配置。
- 模型 probe、cooldown、错误类型分类。
- 章节 index run 记录模型、延迟、错误类型、候选数量。
- 模型健康事件持久化。
- 根据同项目同角色历史健康事件对候选模型排序。
- 写作侧 `fast / pro` 已映射到 writer 角色池。
- fallback / 低置信资产已经开始标记 `diagnostic_seed`、`needs_ai_repair`。

但当前仍有关键缺口：

- 多数任务仍是一轮选择一个模型，没有形成“快模型召回 -> repair 模型修结构 -> deep 模型补强 -> judge 验收”的流水线。
- 同一轮导入中还没有做到按章节、按失败类型、按资产重要性动态切换模型。
- 模型健康排序仍偏“历史优先级”，不是完整的实时竞速和质量评分。
- fallback 资产虽然被标记，但前端和写作 agent 对这些低置信标记的利用仍需要继续加强。
- 部分探测 / 用户可见文案仍存在中文乱码风险，会影响 probe 质量和用户判断。

### 4. fallback 只能保底，不能代表 AI 理解

用户指出的核心问题成立：如果模型失败后系统只是从文章里摘取片段并生成资产，那么 AI 引入的价值就不清晰。

fallback 应该只承担这些职责：

- 保证章节正文不会丢失。
- 保留证据片段，给后续 AI repair 提供定位。
- 生成低置信诊断种子，告诉系统“这里可能有人物 / 关系 / 事件”。
- 支持用户看见失败原因和可修复入口。

fallback 不应承担这些职责：

- 冒充完整角色档案。
- 冒充人物关系理解。
- 冒充世界观归纳。
- 让导入状态从 `low_quality` 升级为 `completed`。
- 直接作为写作 agent 的高质量项目记忆。

正确边界是：规则系统负责稳定召回和定位；AI 负责理解与创作；quality gate 负责阻止低质量结果伪装成可用资产。

更严格地说，fallback 的产物只能有三种身份：

- `chapter_text`：原文资产，可信，但只是正文保存。
- `diagnostic_seed`：诊断种子，只能提示“这里可能存在某类资产”。
- `needs_ai_repair`：待 AI 或用户确认的半成品，不能直接参与高可信写作。

写作 agent 如果读取到 fallback 或低置信资产，trace 必须明确显示；否则用户会误以为 agent 使用的是完整理解后的项目记忆。

## NovelForge 应采用的模型编排策略

### 任务角色池

模型名称不应写死到产品逻辑里，只能作为管理员配置的候选项。产品逻辑应依赖任务角色：

| 角色 | 用途 | 运行策略 |
| --- | --- | --- |
| `extractor_fast` | 全书章节级候选召回 | 小 chunk、较高并发、快速失败、重点看覆盖率 |
| `extractor_repair` | 修复失败章节、空响应、JSON 错误 | 只处理失败章节，按错误类型调整 timeout / chunk / 并发 |
| `extractor_deep` | 补强核心角色、复杂关系、世界观规则 | 低并发、长 timeout，只处理高价值资产 |
| `writer_fast` | 灵感、短段落、轻量改写 | 响应优先，可生成候选草稿 |
| `writer_pro` | 正式序章、关键章节、深度改写 | 质量优先，允许更慢 |
| `judge` | 质量评分、错配检测、写作验收 | 结构化评分，不参与正文生成 |

### 探测和路由层级

实时测速不应只是“打一条 hello”。建议分层：

1. 网关可达：连接和鉴权正常。
2. 短回复可用：非空中文回复。
3. JSON 可用：能输出可解析 JSON。
4. schema 可用：字段满足章节 index 基础结构。
5. 提取有效：小片段返回非空角色、关系、事件、世界观候选。
6. 质量有效：有 evidence、关系张力、角色动机和事件意义。
7. 长输入耐受：目标 chunk 下不空、不截断、不超时。
8. 运行成本：延迟、429/504、并发承载、最近成功率。

路由选择应综合“最近健康 + 当前 probe + 任务角色 + 失败类型”，不能只看速度。

建议路由器保存并解释以下决策字段：

- `role`：本次任务需要的模型角色。
- `candidate_models`：本轮参与候选排序的模型，不暴露密钥。
- `probe_level_passed`：最高通过的探测层级。
- `recent_success_rate`：同角色最近成功率。
- `latency_bucket`：不是单次毫秒值，而是快 / 中 / 慢 / 超时分桶。
- `failure_types`：最近失败原因，例如 `empty_content`、`json_invalid`、`gateway_timeout`、`rate_limited`。
- `selection_reason`：为什么选择当前模型。
- `fallback_reason`：如果没有可用模型，为什么进入 fallback 或 low_quality。

这能避免用户只看到“任务失败”或“模型慢”，却不知道应该换模型、降并发、缩 chunk，还是走 repair。

### 多模型流水线

建议的导入链路：

1. `extractor_fast` 扫全章，目标是高召回候选，不追求完整档案。
2. 规则合并候选，识别低证据、冲突、端点不闭合、空世界观、错配时间线。
3. `extractor_repair` 只修失败章节或结构化失败结果。
4. `extractor_deep` 对核心角色、核心关系、关键世界观做深度补强。
5. `judge` 给最终资产打可写作评分，决定 `completed / low_quality / partial / failed`。
6. 写作 agent 只优先使用通过 gate 的资产；低置信资产只能作为待确认线索。

这条链路比“一个模型跑完整本书”慢一些，但会显著降低网关波动带来的系统性失败。

建议的质量责任分工如下：

| 阶段 | 允许产出 | 不允许产出 |
| --- | --- | --- |
| `extractor_fast` | 高召回候选、证据、粗略关系 | 最终角色性格定稿、最终关系张力 |
| 规则合并 | 去重、端点闭合、候选统计、失败定位 | 伪造语义理解 |
| `extractor_repair` | 修复失败章节、修复 JSON、补缺失字段 | 重跑全书或覆盖已通过资产 |
| `extractor_deep` | 核心角色动机、关系张力、世界观规则 | 大批量高并发扫全文 |
| `judge` | 可写作评分、错配检测、是否完成 | 替代正文生成 |
| writer | 序章、改写、续写、灵感 | 绕过用户确认直接污染内容库 |

这张表应作为后续实现的边界，避免系统再次把所有责任压给一个模型。

### 慢模型使用策略

慢模型应进入深度阶段，而不是被简单淘汰：

- 不用于全书高并发扫描。
- 用于核心资产补强、正式序章、质量判断。
- 降低并发，缩小输入，延长 timeout。
- 记录“慢但成功”和“慢且失败”的区别。
- 连续超时进入 cooldown，但定期重新进入候选。

快模型应负责召回和交互体验：

- 扫章节候选。
- 生成灵感草稿。
- 做低成本预览。
- 失败后尽快切换，而不是长时间阻塞任务。

## 当前状态判断

当前项目已经不再是完全盲跑模型，具备模型路由、健康事件、历史排序、章节级 index、局部 repair、fallback 边界标记这些基础。

但它仍不能被定义为“模型无关、网关稳定”的成熟系统。主要原因：

- 还没有形成完整多阶段模型流水线。
- 质量 gate 能阻止误报，但不能自动把低质量资产修到可写作。
- 写作 agent 已接入 writer 路由，但还没有实现 fast 草稿 + pro 审稿 / 改写的组合模式。
- fallback 标记已入库，但 UI 和 agent 对 `diagnostic_seed / needs_ai_repair` 的处理仍需强化。
- 真实 smoke 仍需要在当前网关和模型池下持续验证，不能只凭单次成功或单次失败下结论。

因此，当前阶段应定义为：

> 模型编排基础已建立，系统正在从固定模型依赖过渡到角色池和健康路由；但提取质量仍需要多阶段 repair / deep / judge 闭环才能稳定达到内部测试可用。

### 隐藏问题清单

除了当前肉眼能看到的提取浅、关系弱、乱码和页面体验问题，后续还需要持续关注这些隐性问题：

- **模型选择不可解释**：如果 trace 不能说明为什么选某个模型，管理员无法判断是网关问题还是策略问题。
- **慢模型误杀**：如果只按 latency 排序，会把适合深度理解的模型排除在关键阶段之外。
- **快模型误用**：如果快模型输出浅摘要但状态仍为 `completed`，写作质量会被系统性拉低。
- **fallback 污染记忆库**：低置信种子如果没有明显标记，会被 agent 当作可靠设定继续创作。
- **质量 gate 只拦不修**：当前 gate 能指出问题，但还需要 repair / deep / judge 自动进入下一阶段。
- **真实烟测样本不足**：单本文本不能证明泛化，需要未来扩展多类型基准，但这不是本轮优先项。
- **网关预算缺少任务隔离**：导入、repair、写作如果共享同一并发预算，正式写作可能被批量提取拖慢。
- **用户可见诊断不足**：用户需要知道“慢但成功”“失败需修复”“只是诊断种子”这些区别，而不是只看到完成或失败。

## 下一步收敛计划

### P0：先修复模型判断和可见性

- 修复探测 prompt / 用户可见文案的中文乱码，避免 probe 本身被乱码污染。
- 前端明确展示 `diagnostic_seed / needs_ai_repair / quality_flags`。
- Extract 页把“模型慢但成功”和“模型失败”分开显示。
- 写作 trace 展示本轮使用的 writer 模型、路由原因和是否使用低置信资产。
- 管理员视图展示模型角色池健康摘要，不要求普通用户手动选择具体模型。

### P1：把导入链路改成多阶段模型流水线

- `extractor_fast` 只负责章节级广覆盖候选。
- `extractor_repair` 根据 `empty_content / json_invalid / gateway_timeout / rate_limited` 修失败章节。
- `extractor_deep` 只补强核心角色、核心关系、世界观规则。
- `judge` 输出结构化质量评分和写作可用性评分。
- 不再允许纯 fallback 资产让状态变成 `completed`。
- 每个阶段必须记录输入章节数、候选数、成功数、失败类型、所用模型角色和下一步建议。

### P2：模型健康从统计升级为决策

- 每个角色维护最近成功率、失败率、平均延迟、错误类型、最近更新时间。
- 路由器按角色读取健康事件，并结合当前 probe 给出选择原因。
- 对 30 RPM 网关预算做任务级限流：导入、repair、写作不能互相抢满并发。
- 管理员面板只配置模型池和预算，不要求普通用户理解模型名。

### P3：写作侧形成组合策略

- 快速模式：`writer_fast` 生成灵感和候选草稿。
- Pro 模式：`writer_pro` 用增强资产生成正式候选。
- 关键保存前可由 `judge` 检查：是否使用角色关系、是否符合世界观、是否有情绪转折。
- 低置信资产参与写作时必须在 trace 中提示，不应隐式当成可靠设定。

## 当前暂停线

在以下能力补齐前，不建议继续大规模新增 UI 或实验功能：

- 导入任务能解释模型阶段和下一步 repair / deep 建议。
- 用户能看到哪些资产只是 fallback 或低置信诊断种子。
- 至少有一个 `extractor_deep` 补强入口，不需要重跑全书。
- 写作 trace 能说明本轮用了哪些资产、哪些模型角色，以及是否使用低置信资产。
- 真实闭环验收能区分“模型慢但成功”和“模型失败不可用”。

这不是暂停产品进度，而是防止继续把功能建在不稳定的提取和模型选择基础上。

## 验收标准

下一阶段不能只看“有没有结果”，而要能回答：

- 本轮导入用了哪些模型，各自负责什么角色。
- 哪些模型慢但成功，哪些模型失败，失败类型是什么。
- 哪些资产来自 AI 理解，哪些只是 fallback 诊断种子。
- 哪些章节需要 repair，为什么需要 repair。
- 角色是否有性格、动机、创伤、欲望和选择压力。
- 关系是否有依赖、误解、债务、冲突、情绪张力和 scene potential。
- 写作 agent 是否使用了通过 gate 的资产，而不是只靠氛围生成。
- 换一个网关或模型池后，系统能否通过探测、健康排序和 repair 继续工作。

如果这些问题无法被系统自动记录并展示，就不能说 NovelForge 已经真正摆脱“换 API 就不可用”的风险。
